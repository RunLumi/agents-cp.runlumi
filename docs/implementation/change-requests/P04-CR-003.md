# P04-CR-003 — Provider dispatch refuses redirects with `manual`, not `error`

Status: accepted for implementation by integration coordinator; merge awaits runtime gates.
Date: 2026-10-09. Affects P04-CG v1 (provider egress), threat model §4, DE2E-INT-05.

## Trigger

The provider HTTP platform lane (`docs/verification/runs/2026-10-07-desktop-managed-e2e/provider-http-platform-handoff.md`,
Finding 1) measured that the provider adapter's `RequestRedirect::Error` cannot be
constructed on the local workerd runtime (1.20260921.1, wrangler 4.137.0): `new Request`
throws `Invalid redirect value, must be one of "follow" or "manual" ("error" won't be
implemented since it does not make sense at the edge; use "manual" and check the response
status code)`. Every provider dispatch therefore failed before any I/O as a bare
`transport_error`, and the cause was discarded.

The frozen intent (P04-CG, P04-BE-03: "redirects rejected", threat model §4: "a 302 to an
internal address is not a hop") is unchanged. Only the mechanism changes.

## Decision

Provider dispatch builds its request with `RequestRedirect::Manual` and treats any 3xx
response as a terminal refusal. `Follow` is never used.

- 3xx maps to `AdapterErrorKind::InvalidResponse` (client code `upstream_invalid_response`),
  `retryable = false`, with the status retained only as `status_code`. A retry would hit the
  same redirect and re-send the credential, so there is no retry and no fallback to the same
  hop.
- The `Location` header is never read, logged, stored, or dialled. No second request is made,
  so the provider credential header is never replayed to a redirect target.
- No upstream body or header text reaches the client, logs, audit or errors (unchanged
  credential and error-body non-disclosure).
- A failed request construction is now logged with the existing redacted
  `provider_dispatch_failure_message` before returning `transport_error`, so this class of
  defect cannot hide again.
- Contract surface is unchanged: no new error code, no request/response schema change, no
  migration, no secret or configuration change.

## Scope boundary (deliberately not changed)

`adapters/webhooks/outbound.rs` still uses `RequestRedirect::Error` (two sites). It is on the
same runtime and is probably affected, but that is UNPROVEN and is a separate webhook
change with its own consequences (delivery semantics, `webhook_redirect_blocked`). It is not
changed here and is recorded as a follow-up, not as a PASS.

Facts and non-facts, kept separate:

- **Measured (local workerd only):** `redirect:"error"` throws at construction; the
  `--redirect-shim` run showed a 3xx returned unfollowed and rejected as non-2xx, with 0
  forwarder denials. The shim run is a workaround diagnostic and is not credited as proof
  about the unmodified adapter.
- **Not proof:** a source-string test cannot show runtime behaviour. The structural test only
  prevents a regression in how requests are built. Hostile redirect behaviour needs the
  unflagged actual-HTTP-adapter run after a build.
- **Not claimed:** supported-runtime behaviour in production, webhook redirect behaviour, any
  external real provider (BLOCKED: no approved key or spend cap).

## Compatibility

Responses that were 2xx or an ordinary 4xx/5xx classify exactly as before. A provider that
answered with a 3xx previously (in theory) either failed at construction or was a followed
hop; it is now a stable `upstream_invalid_response`. Docs for operators: point the
provider base URL at its final, non-redirecting endpoint.
