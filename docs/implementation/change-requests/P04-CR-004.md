# Contract / Plan Change Request — P04-CR-004

Status: **proposed; coordinator decision pending (not accepted, not rejected).** Source
change exists in the shared WIP checkout (see `cancel-lifetime-primary-handoff.md`); no Worker
build, Electron or Node probe has validated it. No runtime PASS is claimed.

Provenance: this text was first written as `P04-CR-003` by the cancel-lifetime primary, which
overwrote the unrelated redirect decision that already held that ID. The redirect decision
was restored to `P04-CR-003`; this proposal was moved here unchanged except for this header,
the ID, and the Decision section. Trigger wording, hypothesis labelling and owed validation
below are the original.

## Trigger

DE2E-INT-05 unshimmed Node runtime proof: the real HTTP socket to the provider
closed ~85 ms after the caller disconnected, yet D1 still showed
`stream_committed` with the reservation held after 90 s. The control that reads the
whole stream completes with held=0. (The `mock://` "cut" that timed out at
21585 ms was a timeout, not a cancel, and is not evidence.)

Source review (`apps/api/src/routes/inference.rs`): the abort listener
(`register_cancellation_finalizer`) and `StreamCancellationGuard::drop` set
`finalized = true` and then `spawn_local` the D1 settlement, discarding its
`Result`. `fetch` in `lib.rs` ignores its `Context`. **HYPOTHESIS, not proven
root cause:** work started from an abort/drop after the client is gone is not
registered with the request's execution context, so the runtime may cancel it,
or the write may fail, while `finalized` already blocks every other settlement
path.

## Affected phase and packets

- Phase: P04 inference router (F10), budget settlement (F11/F13 invariants).
- Contract Gate: P04-CG; no wire contract changes (`inference-v1` unchanged).
- Active dependents: DE2E-INT-05.

## Proposed change

Internal only; no route, schema, status code or error-code change.

1. New adapter `adapters/execution.rs`: `BackgroundWork`, a small explicit port
   around the official `worker::Context::wait_until`. `lib.rs::fetch` moves the
   per-request `Context` into it and passes it to `app::router`, which stores it
   in the per-request `AppState`. No mutable globals, no Tokio.
2. Cancellation settlement (abort listener and stream drop) runs through
   `BackgroundWork::run` so the runtime keeps the request alive until the D1
   write finishes. Without a context (native tests) it falls back to `spawn_local`.
3. The `finalized` flag keeps its once-only meaning but is **released when the
   write fails**, exactly as `finalize_request_once` already does, so a failed
   cancellation write no longer strands the reservation and a later path
   (timeout, stream end, sweeper) can still settle. The failure is no longer
   silent: one bounded line `inference_cancel_finalize:<stage>` with
   `scheduled | ok | err:<ApiError code>`; no ids, org, prompt or secret.
4. Unchanged: CAS once-only request-state/usage/reservation updates in
   `finalize_request`, stale-flag no-retry/no-double-bill, auth, egress and
   budget semantics.

## Why necessary

A disconnect must settle the request and release the reservation promptly
(F10 "cancel upstream where possible", F11 budget holds). A reservation held for
the full expiry window after a user cancel is a budget-correctness and UX defect.

## Compatibility impact

None on wire/schema. Worker gains one `Context` handle per request.

## Alternatives

1. Keep `spawn_local`, only log: leaves the suspected lifetime defect.
2. Durable Object / Queue per cancel: heavier; revisit only if `wait_until` is
   shown insufficient by the runtime proof.

## Revision 2026-10-09: the first hypothesis is already falsified by the replay

The unshimmed Node replay on the build that contained item 2 produced **no**
`inference_cancel_finalize` line of any kind (`scheduled`, `ok`, `err`), D1 stayed
`stream_committed` with the reservation held for 90 s, and the provider socket closed
~84 ms after the cut. So registering `wait_until` *when the abort event or stream drop
fires* did not help: neither callback demonstrably ran. (The original log
`test-results/cancel-lifetime-node-runtime.log` is not in this worktree; the facts come
from the supervisor's report.) The wait_until-at-abort design stays as the settlement
mechanism but is **not** the proposed root-cause fix.

Reading the installed `worker 0.8.6` / `wasm-streams 0.6.0` sources, the body is
Rust stream -> JS stream A -> `worker::Body` (locks A with `IntoStream`, cancel-on-drop)
-> axum body -> `BodyStream` -> JS stream B -> workerd. A disconnect cancels B, and the
drop of the Rust stream (hence the cancellation guard) only happens after two chained
abort-then-wake steps; each needs the request's execution context to still run JS.

**Revised hypothesis H2 (not proven):** the disconnect ends the request's execution
context before any of this runs. Evidence for it from the replay: the stream's own
20 s deadline never settled anything in 90 s either. If the pull future were alive its
50 ms poll loop would have timed out and finalized at 20 s; if it had been dropped the
guard would have traced `scheduled`. Neither happened, which fits a future that is
neither running nor dropped. A second, independent defect was found by reading:
`finalize_request_once` latched `finalized` before awaiting D1, so a pull future dropped
mid-await left the latch set for a write that never finished and blocked every other
path.

### Candidate change for H2 (source only, native tests only)

1. `BackgroundWork::hold()` registers a `wait_until` future when the stream is built
   and releases it when the stream state is dropped. No timer and no new constant: the
   existing request deadline ends the stream, and the platform's own post-response limit
   is the outer bound. It is declared last in `StreamState` so the guard's settlement is
   registered before the hold is released.
2. `LatchClaim`: the once-only latch is now released when a claim is dropped unfinished
   (failed write, or a future the runtime dropped), for both the inline settlement and
   the scheduled one. CAS once-only updates in `finalize_request` are unchanged.
3. Bounded lifecycle trace, fixed words plus elapsed ms only (no ids, org, prompt,
   header, secret), channel check included via `armed`:
   `inference_stream_trace:` `armed:{signal|no_signal|signal_already_aborted}`,
   `abort_event`, `pull_begin/pull_end:<n>:<chunk|eof|error|timeout|cancelled>` (first two
   pulls and every non-chunk end), `pull_dropped_pending:<n>`, `state_drop:{settled|unsettled}`,
   `hold:{registered|released|cancelled_by_runtime}`; and
   `inference_cancel_finalize:` `scheduled|ok|err:<code>|claim_dropped|inline:{start|ok|err}:<reason>`.

## Revision 2026-10-09 (later): the hold is falsified and removed; bounded watchdog replaces it

Retained replay of the H2 build (probe 76301, exit 2; the original
`test-results/cancel-hold-retained-d1/` files are owned by the supervisor and are **not in
this worktree**, so the facts below are the supervisor's report, not read by me):
`armed:signal`, `hold:registered`, pull 1 chunk at 41 ms, pull 2 chunk at 42 ms, then the cut.
No `abort_event`, no `pull_dropped_pending`, no `state_drop`, no `inline:*`, no
`scheduled`. At 20 s workerd logged an uncaught "code had hung and would never generate a
response". D1 stayed reserved 90 s. The provider then completed all 60 frames, where the
build without the hold closed the upstream socket after ~3 frames (~85 ms).

Conclusions drawn from those facts:

- H2 is **falsified**. A request-long `wait_until` that is only released on drop neither
  delivers the cancel/abort/drop callbacks nor settles anything, and it **regressed** provider
  closure (60 frames vs 3). It is removed, not kept as architecture on the strength of unit
  tests (`BackgroundWork::hold`, `Hold` and its tests are deleted).
- In this topology the Rust side is never told about the disconnect: the caller signal did not
  fire, and no cancel reached the body chain (Rust stream -> `wasm-streams` A -> `worker::Body`
  -> axum body -> `BodyStream` -> `wasm-streams` B). `wasm-streams` 0.6 `cancel` only drops the
  source and aborts the pending pull, and `worker` 0.8.6 exposes no cancel hook on
  `Body::from_stream`; a readable-stream `cancel` callback of our own would sit behind the same
  chain and is **not** relied on. Settlement therefore must not wait for a disconnect signal.

**Candidate H3 (source and native tests only, not run in a Worker):**
`BackgroundWork::watch(delay_ms, finalized, settle)` registers one `wait_until` task at stream
start. It races a real timer (`worker::Delay`, an official API, not an idle future) against a
release flag that `Watchdog` sets on drop. On the timer it takes the same `LatchClaim` and
runs `cancel_settlement`, so it writes at most once with the inline, drop and abort paths, and
releases the latch on a failed write. Delay is `max(deadline - now, 0) + 2 s` grace
(`watchdog_delay_ms`), so a live stream's own `request_timeout` path wins first and the
reservation is bounded to ~deadline + 2 s instead of 90 s. The state drop (stream finished or
cancelled) releases the task early. Caller signal, CAS `finalize_request`, budget semantics,
no global state, no Tokio, no queue are unchanged.

Known cost, stated rather than hidden: while the watchdog is registered the request context
stays alive, so on a real disconnect the upstream is closed by the existing provider timeout
signal (<= the candidate `timeout_ms`), not in ~85 ms. If the replay shows the provider still
streaming to completion after the cut, H3 trades closure latency for settlement and a
proper disconnect signal (or an upstream abort controller owned by the stream) is the next
step.

New bounded traces: `inference_stream_trace:watchdog:{registered|released}`,
`inference_cancel_finalize:watchdog:{fired|ok|err:<code>|already_settled}`. The
`hold:*` lines no longer exist.

Replay table for H3 (supersedes the `hold`/H2 rows below; positive control is
`armed:*` and `watchdog:registered`):

| After the cut | Meaning |
|---|---|
| `watchdog:fired` then `watchdog:ok` at ~deadline+2 s, D1 released | H3 settles the reservation; record provider closure time separately |
| `watchdog:fired` then `watchdog:err:<code>` | the write fails: fix that code |
| `watchdog:fired` and nothing after | the write is cancelled mid-D1; the timer path is alive, the D1 call is not |
| `watchdog:registered` and no `fired`/`released` at 20+ s | the timer never fires after disconnect: `wait_until` timers are not honoured here; next is a Durable Object alarm or Queue |
| `watchdog:already_settled` | another path settled first; check which one wrote |
| normal full read: `watchdog:released`, no `fired` | no-cancel control passes |

Required runtime regressions (redacted trace for each): positive capture (cut, settled),
no-cancel full read (state drop releases the watchdog, one settlement), and disconnect
(cut mid-stream). Sensitivity, disposable worktree only: make the watchdog skip the write
and show the disconnect probe fails for that reason.

## Revision 2026-10-09 (final): root cause found: `enable_request_signal` was not set

Root cause of every "no abort_event / pull never dropped" observation above: `wrangler.jsonc`
carried only `nodejs_compat`. In workerd an incoming `Request.signal` fires on client
disconnect only with the `enable_request_signal` compatibility flag (official docs:
<https://developers.cloudflare.com/changelog/post/2025-05-22-handle-request-cancellation/>;
the flag has no default-on date). Without it `worker` 0.8.6's `AbortSignal::from(req.signal())`
yields a signal that never aborts, which is why `armed:signal` printed but `abort_event` never did,
and why the provider's `AbortSignal.any([caller, timeout])` never saw the disconnect (upstream ran all
60 frames). H2 (hold) and the readable-stream-chain hypotheses were not the cause. No Rust change
was needed: the existing abort listener, `schedule_cancel_settlement` and provider signal
composition were already correct.

Change: `apps/api/wrangler.jsonc` `compatibility_flags` = `["nodejs_compat", "enable_request_signal"]`
(shared file, minimal, authorized for this owned execution-port repair). Environments inherit
`compatibility_flags` (no per-env override exists in the file); the production value was **not**
read back from a deploy and no deploy was made. `docs/release/cloudflare-deployment.md` /
ADR 0010 define no flag list; nothing there changed. A production smoke of disconnect remains owed.

Runtime proof (real built Worker, `provider-http-adapter-probe.mjs --outbound=node`, runtime
`/Users/james/.cache/codex-runtimes/codex-primary-runtime/dependencies/node/bin/node` v24.19.0;
build `worker-build --release`, pinned toolchain; `PROVIDER_HTTP_PERSIST_TO` retained D1):

- Result exit 0, all critical claims PASS, including `cancel-settles` and `cancel-upstream-propagation`.
- Upstream: fixture `outcome=client-closed frames=3`, forwarder `upstreamDestroyedBy=response-closed`,
  provider socket closed 85 ms after the cut (was: completed, 60 frames).
- Console (`cancel-signal-retained-d1/worker-console.log`): `armed:signal`, `watchdog:registered`,
  pulls 1-2 at 41-42 ms, `abort_event@84ms`, `cancel_finalize:scheduled`, `watchdog:released`,
  `cancel_finalize:ok` 3 ms later. The watchdog did **not** fire; this is the abort path, not the fallback.
- D1: `state=failed error=request_cancelled reservations=released held=0`. The probe's
  `settledWithin=2738ms` is its poll granularity (bound 20000 ms, unchanged); the write itself
  was ~3 ms after the abort per the console.
- Sensitivity (same build, flag removed only): exit 2, no `abort_event`, 60 frames, settled
  24506 ms, `cancel-settles` and `cancel-upstream-propagation` UNPROVEN. Logs kept:
  `cancel-signal-sensitivity-noflag-runtime.log`.
- Earlier evidence preserved unchanged: `cancel-watchdog-runtime.log` (21637 ms, watchdog),
  `cancel-hold-*`. Runs on Node 22 (`cancel-signal-runtime-node22-INCOMPLETE.log`,
  `cancel-noflag-node22-INCOMPLETE.log`, `cancel-signal-runtime-attempt1-harness-fetch-failed.log`)
  hit a harness ECONNRESET on keep-alive and are incomplete, not product failures.
- Native: `adapters::execution` 11 passed, `routes::inference` 24 passed; WASM release build OK.

Still UNPROVEN / not claimed: the advisory `cancel-mock-control` (mock:// provider disconnect
reclaimed at 23550 ms; a mock provider has no upstream socket, cause not diagnosed); production
Worker disconnect behaviour; the 20 s bound is unchanged and was not raised. The bounded watchdog
remains as fallback.
