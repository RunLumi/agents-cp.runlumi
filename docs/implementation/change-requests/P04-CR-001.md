# Change Request — P04-CR-001

- Status: accepted for this desktop integration goal; exact merge still follows the P04/P05 owners' gate and PR review.
- Date: 2026-10-07.
- Requested by: desktop/backend integration coordinator.
- Base contract: P04-CG v1, P05-CG v1, P05-CR-002.
- Affected packets: DE2E-INT-04, DE2E-QA-01.

## Trigger

The frozen P05 device APIs create a durable device-bound Session and Run, and
the frozen P04 OpenAI-compatible route is the client adapter used by
`lumi-managed-inference`. The desktop's existing helper emits
`X-Project-ID`, `X-Device-ID`, `X-Agent-Session-ID`,
`X-Run-ID`, `X-Agent-Definition-ID` and
`X-Agent-Definition-Version`. Source inspection of
`apps/api/src/routes/inference.rs` shows that `ChatRequest` has no P05
context fields and `chat_request` discards them; `run_inference` only
resolves a run when `NativeRequest.run_id` is present. Therefore a real
OpenAI-compatible LumiAgents request cannot currently link its P04 inference
and usage rows to the P05 device run using the production adapter.

## Proposed additive contract

Keep both existing P04 request bodies and routes unchanged. Treat the six
optional P05 headers above as untrusted correlation/lookup inputs. If any are
present, validate shape and resolve all requested run/session/project/device/
agent-definition/version fields against the existing D1 Run, Session,
WorkspaceBinding, Device, AgentDefinition and current PolicySnapshot before
provider selection or dispatch.

For the native route, body fields remain supported. If an equivalent header and
body field are both present, disagreement fails with the stable managed-scope
denial. For chat completions, populate the server's internal request scope from
these headers. A supplied P05 context requires a Run ID; an Agent Session ID
without Run ID is refused. The server replaces/derives project, device,
principal, agent-definition/version and policy from stored rows. Header IDs
never select an organization, grant membership, bypass P04 `inference.use`,
or establish the authenticated P02 principal.

The P02 login session remains `inference_requests.session_id`. P05 work
correlation remains `agent_session_id`; P04 `request_id` remains server
generated. Normal non-managed P04 requests and request bodies retain their
current behavior.

## Compatibility and security

- API: additive optional headers only; no request/response body change.
- Database/migration: none. Existing P04/P05 columns already store the
  validated identities.
- Existing clients: unchanged requests continue through the original P04 path.
- Security: current P02 session/Bearer and centralized `inference.use`
  authorization remain mandatory. Run resolution validates same principal,
  alias, agent session, org/project/device/binding and policy before dispatch.
- Accounting: the existing managed-run reservation is reconciled with the P04
  request ID; no client-controlled cost/reservation value is introduced.

## Alternatives

1. Change P04 ChatRequest to add several optional JSON fields. This changes the
   frozen body schema and duplicates P05 correlation fields beside the existing
   standardized headers.
2. Route the client through P04 native Responses by translating standard
   OpenAI request and response streams in a new provider adapter. That duplicates
   protocol conversion already provided by LumiAgents' OpenAI-compatible
   adapter and creates a larger compatibility surface.

The existing P05 correlation headers plus server-side D1 resolution are the
smallest additive path.

## Verification obligations

Positive control: create a real P03-bound P05 device session/run and a P04 route,
then issue an OpenAI-compatible request with matching headers; read P04 request,
usage and P05 RunEvent/D1 rows. Negative controls mutate each scope axis and
prove refusal before provider dispatch. Existing session-only chat requests
remain accepted. Run proof must also cover revocation, terminal run, stale
policy and mismatched body/header pairs. A direct Worker request is supporting
evidence only; DE2E-INT-04 still requires the actual Electron/agent/provider path.

## Decision

## Runtime compatibility addendum (2026-10-07)

Actual Electron/AI SDK requests exposed additional contract gaps. Chat request
parsing now accepts strict stream_options.include_usage and automatic
tool_choice only (other choices fail closed). The tool count bound is 128 with
the existing 128 KiB combined schema bound unchanged. This is an intentional
request contract update, superseding the header-only/no-body-change statement
above for these named fields.

Successful Chat SSE chunks omit the error property entirely: the SDK treats
even error:null as an error. Requests opting into streaming usage receive a
usage-only final chunk with prompt_tokens, completion_tokens and total_tokens
before DONE. The backend retains its own usage accounting. Existing chat
clients keep their path; native Responses is unchanged. Focused parser/chunk
tests and the Electron stream reproducer are required before merge.

Accepted for implementation by the active goal coordinator on 2026-10-07 as an
additive contract clarification. Re-review against P04/P05 owner and PR policy
before merge. This decision does not authorize deployment or relax any existing
gate.
