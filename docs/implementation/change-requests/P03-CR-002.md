# Contract / Plan Change Request — P03-CR-002

## Trigger

DE2E-INT-02 runtime proof shows the P03 device token expires after fifteen
minutes, but the only nonce endpoint for proof refresh requires a live token.
The desktop cannot resume managed work after expiry. The anonymous nonce weakness
V01-019 is closed; silently reenrolling another key or restoring that endpoint
would violate the current security boundary.

## Affected phase and packets

- Phase: P03/P08 desktop integration follow-on.
- Contract Gate: P03-CG `p03-cg-v1`; this is an additive accepted addendum.
- Active dependents: DE2E-INT-02 and later desktop E2E packets.
- Merged dependents: existing P03 device/token/policy implementation and V01-019.

## Proposed change

Keep routine `GET /api/v1/devices/token/nonce` + signed refresh unchanged.
Add explicit human-authorized recovery:

1. `POST /api/v1/orgs/{org_id}/devices/{device_id}/recovery-challenges` requires
   current Lumi session, CSRF, Idempotency-Key and either devices.manage or the
   enrolling member. It returns a five-minute challenge. D1 stores its hash,
   org/device/requester, expiry and consumption state; a newer challenge replaces
   outstanding challenges for that device atomically. The raw challenge is
   proof material, never a credential.
2. `POST /api/v1/orgs/{org_id}/devices/{device_id}/recover-token` uses the same
   current human authorization and CSRF. The original device key signs
   `lumi-device-token-recovery-v1\n<device_id>\n<challenge>`. Recheck org/device/
   enrolling-member/client-version state. One D1 batch consumes the challenge,
   invalidates old tokens, stores one new token hash and appends an audit event.
   A consumed/expired/replaced challenge cannot mint another token. If the reply
   is lost, the user explicitly requests a fresh challenge.

No anonymous recovery endpoint is added. Expiry pauses managed operations;
local personal work remains usable. Desktop never retries recovery automatically.

## Why necessary

The actual desktop flow confirmed there is no route to recover after its device
token expires. Reusing enrollment is invalid because its state is completed and
it would create a second identity; reopening anonymous nonce issuance would
reintroduce V01-019. A current human session supplies intent/authorization while
the enrolled key proves device continuity.

## Compatibility impact

- API/schema: additive routes and migration 0025; existing refresh is unchanged.
- Client: explicit recovery action and domain-separated proof.
- Security: session+CSRF+org permission/self authority+key proof+active device/org/
  member/version fences+one-time atomic consumption+rotation+audit.
- Data: new hashed expiring challenges; forward-only additive migration.
- Existing clients continue routine token refresh and local operation.

## Alternatives

1. Restore anonymous nonce: rejected; violates V01-019.
2. Enroll a second key silently: rejected; changes device identity and can collide.
3. Clear local state/reinstall: rejected; sacrifices existing user work.
4. Explicit human-authorized single-use challenge, proven by the original key:
   accepted for this integration goal.

## Decision

Accepted by the P03/P08 integration coordinator. Implementation is subject to
review in the control-plane PR. STATUS.md remains owned by its phase coordinator;
the follow-on is tracked in docs/implementation/desktop-e2e/plan.md.
