# P05 Change Request — P05-CR-004

- Status: accepted; backend implementation in progress, runtime proof pending.
- Date: 2026-10-07.
- Base contract: P05-CG v1, P05-CR-002 §4, P05-CR-003.
- Owner: integration coordinator.
- Write surface: tools result/broker routes and repositories, additive migration,
  private client tool transport, Core gate and actual runtime verification.

## Demonstrated source gap

P05-CR-002 promises atomic per-use consumption before returning `allowed`.
`record_tool_result` currently accepts only completed/failed/cancelled and consumes
the grant while recording that terminal result. It supplies no pre-execution
permit, and decision replay can still report an approved allow. Client integration
must not turn that replay into handler execution. The new private transport
therefore continues to refuse approval-based allows until this repair is proven.

## Preserve the existing resource and path

Use `ToolCallRef` as the once-only execution record. Extend the existing device
result endpoint with `status: allowed` as the pre-execution action promised by
CR-002. Require the exact bounded decision request, argument-summary hash and
policy version for that action. A client status never grants authority: re-evaluate
the existing broker's current catalog, agent, runtime, org/project/device policy,
membership and run scope before considering the claim.

An additive migration records nullable execution start time, execution device
and policy version on ToolCallRef. The D1 batch must atomically assert an unclaimed
allowed call and current scope/binding, claim it once, consume the exact live
per-use approval when applicable, and append timeline/audit/outbox evidence.
Session approvals remain reusable only for their exact approved scope/arguments;
each individual tool call still gets one execution claim.

[ADR 0013](../../adr/0013-tool-execution-claim.md) records custody and rollback.
Migration 0027 adds the claim fields with complete-shape and immutable-binding
triggers. Older refs remain unclaimed; do not backfill fabricated execution proof.

Guard the catalog/agent and each applicable policy layer against changes between
evaluation and commit. Do not rely only on the maximum of unrelated policy
versions. The stored argument hash must bind the canonical summary containing the
complete client input digest. No raw argument, path or output is stored for this
claim. Failed guard/CAS leaves all business effects and grant consumption unchanged.

A duplicate pre-execution request must not return another executable allow,
including idempotency replay after a lost response. Unknown delivery/execution is
an explicit reconciliation state; a new call/grant is not silently synthesized.
The claim fields cannot be reset or moved to another device. Terminal result
reporting follows the claim and never consumes a grant after the handler ran.
Completed without a claim is refused; failure/cancellation before admission may
be recorded without authorizing execution or consuming approval.

Terminal-result clarification: completed, failed and cancelled are all terminal.
Same-status reporting may replay without another audit write; a different terminal
status must be refused with stored state/audit unchanged. In particular, a late
failed report cannot acknowledge a transition from completed when the guarded
UPDATE cannot change that row. This preserves the existing terminal invariant.

Result commit must also assert the observed non-terminal status in the same D1
batch as the status update and audit/outbox. A pre-read alone cannot arbitrate
concurrent completed/failed/cancelled reports. A same-status winner may replay its
stored projection; a conflicting winner returns tool_result_conflict without a
second audit write or a fabricated successful transition.

## Client and compatibility

Capability-race clarification: capture the bounded effective platform/org
capability tuple list (ID, key, risk class, version) before evaluation. Recompute
that same ordered list inside the claim transaction and require exact equality.
Additions, removals and reclassification/version changes must invalidate the
claim even when all tool/policy maximum versions are unchanged. Use the same
500-row bound and deterministic ordering as the evaluator. No client-supplied
catalog binding, wire/schema change or new authority is introduced. This guard
is separate from scope/policy guards to preserve D1's expression-depth budget.

Main retains DeviceToken custody. The private adapter releases an allow only
after the pre-execution batch succeeds and returns the exact run/call/tool/hash/
policy binding. Core checks cancellation and input binding immediately before
handler admission and passes an isolated approved JSON snapshot to the handler.
Result reporting uses bounded status/error metadata; no raw output forwarding.

Older client requests remain readable, but an old completed-without-start flow is
refused. New clients fail closed against backends lacking pre-execution support.
After claims exist, rollback must retain the claim-aware backend; never clear
claim/consumption fields as a recovery shortcut. Backend-first delivery and the
exact paired compatibility test remain required.

## Required proof

Implementation checkpoint: the allowed preflight path exists and claims scope,
live token, catalog/agent versions and individually observed policy/MCP records
before consuming approval in the same transaction. The first real D1 control
failed because one combined predicate exceeded D1 expression depth 100. Preserve
the original error. Scope and policy are now separate guard statements inside
the same transaction; no predicate or consumption gate was removed. Runtime
reproducer is being rerun before any client approval-based allow is enabled.

Follow-on proof: backend and actual private client preflight are runtime-proven
in the dated verification record. Pending remains pending; an allow is released
only after an exact bound claim response. The actual adapter race has one winning
allow, consumption is observed before harness-owned file I/O, and replay refuses.
This is not automatic approval waiting/result reporting or Electron tool proof.

Actual Worker/D1 plus real handler positive control; pending, denied, expired,
wrong arguments/tool/run/device/session/policy and duplicate concurrent starts
produce zero handler effects. One winning start consumes one per-use grant
before the handler writes. A second start cannot execute. Policy/catalog/device/
membership changes between evaluation and commit lose the claim atomically.
Terminal result, cancellation, network ambiguity and restart preserve the once-only
record. Mutating each load-bearing guard must make the verifier fail for the
intended reason, with positive controls and original failing evidence retained.
