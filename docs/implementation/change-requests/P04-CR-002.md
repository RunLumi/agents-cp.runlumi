# P04-CR-002 — Preserve OpenAI-compatible tool turns

Status: accepted for implementation by integration coordinator; merge awaits runtime gates.
Date: 2026-10-08. Affects P04-CG v1, DE2E-INT-04 and QA.

## Trigger

Actual Electron text inference PASS does not prove tools. Source inspection of
ChatMessage/chat_request shows assistant tool_calls and tool tool_call_id are
rejected by deny_unknown_fields and null assistant content fails conversion.
ProviderStreamEvent::ToolCallDelta retains only ID/arguments. OpenAI decoder drops
function name/index and chat renderer converts native tool delta to empty content
with terminal stop. A real model tool turn cannot survive this gateway.

## Proposed change

Preserve bounded typed assistant function tool_calls, nullable assistant content
when valid calls exist, and tool tool_call_id through request validation, internal
message representation and OpenAI-compatible provider serialization. Retain strict
unknown-field refusal. Tool message requires a valid referenced call ID; other
roles cannot borrow tool fields. Enforce unique call IDs, exact function type,
bounded names/IDs/JSON argument strings, at most128 calls and existing aggregate
request content limits. No arbitrary unvalidated Value passthrough.

Frozen implementation bounds:128 calls,128 UTF-8 bytes per call ID/name,
256KiB argument JSON per call,512KiB aggregate arguments per response, and
512KiB aggregate request message content including tool IDs/names/arguments.
Call IDs use ASCII letters/digits plus underscore/hyphen/dot/colon; names are
non-empty and reject controls. These gateway limits do not relax the stricter
managed executor's own admission/argument-summary limits.

Streaming carries index, optional ID/name fragments and argument fragments without
substituting an ID when provider omits it on subsequent chunks. Preserve terminal
finish_reason tool_calls and independent usage-only chunks; ordinary text retains
stop semantics. Invalid/corrupt fragments fail closed. Tool output is meaningful
output: no fallback/retry after it. Native protocol remains compatible where
possible; additive fields do not change tool execution authority.

Gateway does not execute tools or resolve approvals. P05 device/current scope,
capability catalog, policy, grants, atomic claim and automatic result still apply.
Tool arguments/results remain request content under existing privacy policy;
never place them in audit metadata/logs.

Development-only mock tool fixture may emit a bounded synthetic write call chosen
from actual request.tools, then terminal text after its matching tool result. It
must remain impossible in production, have bounded rounds and use only disposable
fixture paths/content. This is gateway/desktop integration evidence, not external
provider proof.

## Compatibility and merge protocol

Old text requests/responses stay valid. Native message fields are additive/optional;
old tool grants do not become new permissions. No data migration, secret or
production configuration change. Backend merges before dependent client pin.
Update F10 and fixtures; retain all existing authorization/tenant/budget gates.

## Required evidence

Strict request matrix (valid assistant+tool round trip, wrong role, unknown fields,
duplicate/unmatched IDs, oversized/invalid args); chunked decoder→chat renderer
round trip with interleaved calls and usage; no fallback after tool output;
production mock refusal; real Electron Agent model tool→Main→Worker claim/approval
→actual handler→stored result/audit plus denied no-effect case. Missing proof
remains UNPROVEN; unit/decoder tests alone do not prove Electron tools.
