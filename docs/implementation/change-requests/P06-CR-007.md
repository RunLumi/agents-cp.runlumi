# Contract / Plan Change Request — P06-CR-007

Conformance repair for DE2E-INT-05. **No frozen wire shape changes.** Claimed by the
DE2E-INT-05 implementer; the coordinator owns STATUS and may renumber.

## Trigger

Fresh replay `scheduler-json-fixed` (retained profile `uAlKcL`): with the CR-006 queue
repairs the real chain worked up to dispatch -- JSON sender -> real queue -> consumer
`p06_automation_job:automation.dispatch:dispatch_applied:dispatched`, job `succeeded`,
occurrence `dispatching` -- and then nothing: the desktop polled
`GET /devices/automations/due` -> `200` every cycle and never called `claim`.

Cause, read from the stored rows and both sides' source:

1. The dispatching occurrence has `policy_snapshot_id = NULL` and `policy_version = NULL`.
   Generation (`generate_for_automation`) and manual run (`run_now`) both insert them as
   `None`, and nothing ever sets them.
2. `due_projection` emits the row's values unchanged, so the wire carries `null`.
3. The client's `listDue` requires `policy_snapshot_id` to be a string and `policy_version`
   an integer (`automationLeaseTransport.ts`), and throws `automation_wire_invalid` for the
   **whole list** before any claim.

## Why the client is right and the Worker deviates

The frozen contract requires the values:

- `docs/contracts/p06-automation-lease-v1.md`: `P06AutomationOccurrenceRef` lists
  `policy_snapshot_id` and `policy_version`; the client strict schema requires
  `pol_...` and a positive integer.
- `P06-CG.md` (Occurrence): "The occurrence stores the server-resolved execution
  principal, P06 policy snapshot/version, and off-peak mode so P05 run/tool/inference
  admission can re-evaluate the same trusted context."

The earlier comment on `due_projection` ("authoritative execution context comes from the
`start` call") is not borne out: the `start` grant carries no policy
(`{occurrence_id, attempt, run_id, agent_session_id, lease_id, lease_version, lease_fence,
expires_at}`), and `start_occurrence` creates the P05 run with the occurrence's own
`policy_snapshot_id/policy_version` -- i.e. `NULL`.

So loosening the client decoder would not make the chain work, only move the refusal:

- Main's activation guard already refuses a run whose policy is `null` or differs from
  the claimed occurrence (`lumiManagedAutomationActivation.ts`, `run without policy`).
- P05 tool admission requires the run's `policy_snapshot_id` to equal the org's **latest**
  snapshot and the device to have acknowledged it (`repositories/tools.rs`), which a
  `NULL` run can never satisfy.

Filling a default or accepting `null` on the client would fabricate policy authority the
server never issued. That is rejected.

## Affected phase and packets

- Phase: P06, consumed by DE2E-INT-05. Contract Gate `p06-cg-v1` unchanged.
- Dependent packets: DE2E-INT-05 (client scheduler). Client strict schemas stay as they are.

## Proposed change

Current: occurrences reach `dispatching` with no policy snapshot/version.

New: when `automation.dispatch` moves a `pending` occurrence to `dispatching` it also
binds, in the SAME D1 batch, the org's **latest published policy snapshot** (id and
version) read at that moment.

- Only on the dispatch edge. `queue_one` / `cancel_previous` holds, `skipped`, `missed`
  and `blocked` outcomes are not bound.
- Every dispatch re-binds the current latest, including a requeued occurrence (lease
  expired before start), so a retry never carries a stale snapshot. The statement is
  limited to `state = 'pending'`; a started or terminal occurrence is never rewritten.
- If the org has no published snapshot there is nothing authoritative to bind: the
  occurrence is recorded `skipped` with the stable reason `policy_snapshot_unavailable`
  instead of being dispatched with `NULL`.
- `due`, `claim` and `start` then carry real values with no code change; the run created
  by `start` inherits them, so Main activation and P05 admission see the same trusted
  context. If policy is republished after dispatch, P05 admission fails closed against the
  newer snapshot, which is the intended freshness rule.

Unchanged: the client strict decoders, the claim/start/settle/release wire, the direct
claim route, entitlement and overlap decisions, lease fencing.

## Client conformance obligations (no wire change)

- A due item with a `null`/absent policy remains `automation_wire_invalid`: it is never
  claimed, never defaulted, and no lease is requested.
- The due check enforces, BEFORE any `claim` request, exactly what the claim decode later
  enforces (`pol_` snapshot ID, positive integer version, `occ_`/`aut_` IDs, non-negative
  attempt). Previously a malformed-but-string value passed the due check, was granted a
  lease by the Worker, and only then failed the decode: a leaked lease and a spent attempt.
- Not part of this repair, recorded as a follow-up: one malformed item still fails the
  whole `due` list, so a bad row hides valid siblings and shows as a repeating
  `due 200 / no claim` rather than a per-item `wire_invalid` skip.

## Why this is necessary

Without it no scheduled or manual occurrence can ever be claimed by the real desktop, so
managed scheduled execution cannot run end to end.

## Compatibility impact

- API/wire/schema/migrations: none. The policy columns already exist, are nullable and
  have no immutability trigger; the new statement is an `UPDATE` of two existing columns.
- Existing data: occurrences already `dispatching` with `NULL` policy stay unclaimable by
  a strict client and are resolved by lease/occurrence expiry; new dispatches are bound.
- Security: strictly narrower than before. No client-supplied value gains authority.

## Alternatives considered

1. Accept `null` policy in the client and fill it from the device's own snapshot:
   rejected -- fabricates authority and fails later at activation/P05 admission anyway.
2. Make `start` return policy and bind there: rejected as the primary fix -- the frozen
   shape needs it at `due`/`claim`, and `due` could never decode before `start`.
3. Bind at generation: rejected -- the slot may wait for hours; the policy must be the
   one current at dispatch.
