# Contract / Plan Change Request — P06-CR-004

Client conformance clarification for DE2E-INT-05. No frozen wire shape changes.
Claimed by the DE2E-INT-05 implementer; the coordinator owns STATUS and may renumber.

## Trigger

Implementing the desktop scheduler against `p06-cg-v1` produced three facts the
frozen text leaves implicit:

1. `POST /devices/automations/occurrences/{id}/start` creates the P05 run in state
   `queued` (`INSERT_AUTOMATION_RUN_SQL`, `apps/api/src/repositories/automations.rs`).
   The Contract Gate says only that the run "durably exists" in the start response.
   Nothing says who moves it to `running`, but P04/P05 inference admission requires a
   `running` run with a `request_id`. The desktop must call the existing P05 device
   `start` route for that run.
2. Settlement order is not stated: P05 terminal state and P06 `settle` are separate
   device calls with no cross-transaction.
3. An older desktop build that has no knowledge of the client-side adoption marker
   would execute the local original next to the active managed copy. The Gate is a
   server contract and cannot prevent that; the guard has to be client-local and
   storage-enforced (see client spec 07 "Downgrade compatibility guard").

## Affected phase and packets

- Phase: P06 (consumed by DE2E-INT-05)
- Contract Gate: `p06-cg-v1` (+ CR-001/002/003) unchanged
- Active dependent packets: DE2E-INT-05
- Merged dependent packets: none changed

## Proposed change

Current: P06 start returns a grant; execution/settlement ordering is unspecified for
the client.

New (client obligations only):

- After `start`, the host calls P05 `GET run` and P05 `start` (`queued → running`)
  before any inference or tool use, and validates run, session, org, device, project,
  binding and policy snapshot/version against the grant and current authorization.
- Terminal order: P05 `complete|fail|cancel` first, then P06 `settle`. A failed or
  lost settle leaves the occurrence for the server's lease-expiry to classify
  (`ambiguous`); the client never retries execution or re-settles over newer state.
- Any failure after the start grant is settled as `failed` with a stable reason code;
  `release` remains pre-start only.
- `off_peak` occurrences are not claimed by a host that cannot enforce the narrowed
  tool constraints.
- Client storage carries a database-level claim guard for adopted originals
  (client migration 0005) so builds that ignore the marker table cannot claim them.

## Why this is necessary

Source evidence: `start_occurrence` inserts the run with state `'queued'` and the
device `transition` handlers allow `queued → running` for any run owned by the
device. Without step 1 the first inference request is refused. The downgrade
reproducer `docs/verification/runs/2026-10-07-desktop-managed-e2e/evidence/automation-downgrade-query-reproducer.log`
shows the pre-guard selection still returns an adopted original.

## Compatibility impact

- API: none; existing device routes only.
- schema: none on the Worker. Client SQLite gains a trigger and a journal table.
- FE fixtures/types: none.
- LumiAgents protocol: one private Main→Host message and one Host→Main reply
  (`lumi-managed-automation-run`, `lumi-managed-automation-run-result`).
- migrations: client `0005_automation_managed_guard`, additive; 0004 unedited.
- security: Main stays sole holder of session, device token, lease token and fence.
- existing data: originals and their history are never rewritten.

## Alternatives considered

1. Let the Worker create the P05 run as `running`: rejected, it would assert execution
   began before the host accepted the grant and change a frozen transition.
2. Rely on "unknown ledger rows are ignored" for old builds: rejected, it is the
   defect being fixed.
3. Server-side kill switch for old clients: rejected, no per-client identity exists
   in P06 and it would be a frozen-contract change.
