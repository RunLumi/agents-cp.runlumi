# P03-CR-004 — Desktop runtime capability report completeness

Status: accepted for implementation by integration coordinator; merge awaits runtime proof.

## Trigger

DE2E-INT-04 uses actual runtime descriptors whose filesystem/process/network/MCP
capabilities are mandatory. Device report validator accepts only browser_use,
computer_use, remote_environment and automation_eligible. P05 translates only
these four toggles. No platform catalog rows exist for the other four classes.
Thus real managed tools cannot satisfy runtime support without weakening their
requirements. Desktop private device transport has no heartbeat command yet.

## Affected phase and packets

P03-CG v1, P05-CG v1, DE2E-INT-04 and integration QA. Coordinator owns bounded
device report validation, capability catalog migration, P05 runtime mapping,
private desktop heartbeat transport and Main reporting lifecycle.

## Proposed change

Add optional boolean filesystem_write, process_execution, network_access and
mcp_execution to the existing heartbeat capability object. Map them to catalog
keys filesystem, process, network and mcp respectively. Missing/false remains
unsupported. Preserve all existing toggles and bounded payload validation.
Seed platform definitions in a new forward-only migration with deterministic
IDs matching the runtime's existing capability-ID derivation. Do not edit0023.
Main reports only capabilities its owned Host/runtime actually exposes; renderer
and model cannot supply or override reports. Unknown availability reports false.
Use the existing device heartbeat API; no alternate inventory or policy owner.
Catalog identity, current grant, policy, run scope and execution claim remain
independent requirements. Capability support alone never grants use.

## Compatibility impact

- API: additive optional keys; old clients retain current behavior.
- Schema: additive platform rows only; no customer data rewriting.
- Older backend: rejects new keys; client must fail closed and require compatible
  backend rather than silently remove required capabilities.
- Existing reports: absent added toggles do not grant new support.
- Client: private Main/device transport, no DeviceToken or paths in renderer.
- Tool identity: preserve existing hashes for the four new catalog classes;
  browser/computer use the existing migration0023 platform IDs.

## Alternatives considered

Dropping requirements or inferring filesystem support from automation_eligible
would permit unsupported execution. Reject both. A new capability inventory API
duplicates the existing bounded heartbeat and is unnecessary.

## Merge protocol and proof obligations

Backend contract/catalog must merge before dependent client delivery. Validate
strict types/unknown keys; old report compatibility; false/missing refusal;
positive real heartbeat → catalog → P05 execution claim; cross-device/tenant
negative controls; report changes invalidate stale admission. Actual Electron
Main/Host tool execution is required separately. No completion from unit tests.
