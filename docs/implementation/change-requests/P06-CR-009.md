# Contract / Plan Change Request — P06-CR-009

## Trigger

Phase 2 hostile probe `S5-T6` (`docs/verification/phase02-workspace-hostile-probe.md`) could never reach
its positive control: after the real cron sweeps an occurrence created by `POST .../run-now` stayed
`pending` and its `automation.dispatch` row in `queue_job_envelopes` stayed `queued`
(`attempt = 1` is the INITIAL value written by `INSERT_QUEUE_JOB_SQL`; it proves nothing about publishing).
Source reading, confirmed by independent review (`phase02-queue-replay-review-20261009.md`):

1. `lib.rs::dispatch_due_data_jobs` publishes only `export.run` / `deletion.run`; nothing publishes
   `automation.dispatch` to `JOBS_QUEUE`.
2. `consumers/automations.rs::AutomationJobHandler::run_sweep` maps BOTH `Dispatch` and `ExpireLease` to
   `run_lease_expiry_sweep`. `jobs/automations.rs::dispatch_occurrence_statements` (the frozen
   dispatch-time recheck, version guard, overlap effects and lifecycle events) has no caller.
3. `DEVICE_DUE_OCCURRENCES_SQL` and the lease contract (`pending|dispatching -> leased`) require a
   server-written `dispatching` state that no runtime path produces except the claim's internal edge.

So the frozen contract (`automation.dispatch` job type, occurrence `pending -> dispatching`) is specified
but unwired. A producer alone is insufficient.

## Affected phase and packets

- Phase: P06 (consumed by the Phase 2 desktop/backend E2E candidate)
- Contract Gate: `p06-cg-v1` (no frozen wire or schema change)
- Active dependent packets: Phase 2 server candidate (`docs/implementation/desktop-e2e/phase02-server-candidate.md`)
- Merged dependent packets: P06 automation job handler (behavioural completion only)

## Proposed change

Current: no producer for `automation.dispatch`; the `Dispatch` handler runs a global lease-expiry sweep.

New (write surface expansion, minimal):

- `apps/api/src/lib.rs`: `dispatch_due_data_jobs` also publishes due `automation.dispatch` envelopes as the
  frozen `QueueJobEnvelope` (tenant scope from the persisted row, bounded payload `{occurrence_id}`).
  Delivery is at-least-once; the consumer claim is the dedupe.
- `apps/api/src/consumers/automations.rs`: `JobType::Dispatch` becomes subject-scoped. It reads the durable
  job row (authority for tenant and subject, envelope hint must agree), re-reads the occurrence and
  automation tenant-scoped, re-reads dispatch eligibility, resolves the overlap plan, and commits
  `[job claim, dispatch_occurrence_statements.., job complete]` in ONE guarded D1 batch. Occurrence
  `state_version`, job `lease_version` and eligibility asserts roll everything back together. A
  `queue_one` / `cancel_previous` plan keeps the occurrence `pending`, schedules a bounded job retry in
  the same batch and acknowledges the message. `ExpireLease` and `GenerateOccurrence` are unchanged.
- `apps/api/src/routes/projects.rs`: an authorized same-key replay of the admin binding unbind re-runs the
  idempotent, payload-gated policy refresh before answering the stored `204` (S5-T9).

## Why this is necessary

Runtime evidence: S5-T6 BLOCKED (occurrences `pending`, envelopes `queued`) and S5-T9 FAIL
(`phase02-workspace-hostile-s5t9-original.log`, 123/125). A schedule cannot become due, and an automation
pinned to a removed binding cannot be shown refused, without a real dispatcher.

## Compatibility impact

- API: none (no route or response change).
- schema: none; no migration.
- FE fixtures/types: none.
- LumiAgents protocol: none; the due list now becomes non-empty as the contract already described.
- migrations: none.
- security: dispatch-time recheck is the frozen one (org state, principal membership, policy version,
  license, entitlement). Tenant comes from the stored row; a message org that disagrees is a permanent
  `queue_job_scope_mismatch`. No state is seeded and no eligibility is relaxed.
- existing data: pending occurrences created before the fix are dispatched on the next tick.

## Implementation note (measured)

`Queue::send` of a `serde_json::Value` object is delivered as `{}` under local `wrangler dev`; the producer sends the typed
`QueueJobEnvelope` instead and omits the payload. Runtime evidence: `test-results/phase02-workspace-hostile-final.log` (130/130).

## Alternatives considered

1. Producer only: leaves the handler running a lease sweep; occurrences stay `pending`.
2. Dispatch directly from the cron without the queue: bypasses the frozen job/dedupe contract.
3. Seed `dispatching` in D1 from the probe: forbidden (execution-authority bypass).
