# Contract / Plan Change Request — P05-CR-005

Status: **proposed**. Step 1 (fail closed, within the current contract) is implemented in
LumiAgents `91db7fb4` + `e9c1ffc2` (PR #49); steps 2–3 change the frozen contract and await the P05 owner.

## Trigger

`tests/integration/desktop-browser-electron.mjs` (2026-10-12, Linux, actual Electron app, fresh
Worker/D1) drives the shipped Browser Use tool `mcp__node_repl__js` in a managed run. The model's
fixed snippet runs the documented bootstrap and opens a harness-owned loopback page that counts hits.

- Positive control: the org reviewed the exact runtime descriptor, approved the `node_repl` server,
  allowed the tool and the `127.0.0.1` domain, and approved the per-use request → exactly one hit.
- **Fault:** with the tool still allowed and the call approved, the org's browser policy blocked
  `127.0.0.1` (`allowed_domains: []`, `blocked_domains: ["127.0.0.1"]`). The page was still hit
  once, and the call completed with an execution claim by the device.
- Controls that held: the tool outside the agent allowlist was refused (`agent_tool_not_allowed`)
  and a denied per-use approval was refused, both with 0 hits.

So FR-F13-005 browser controls (allowed/blocked domains, download, upload, authenticated browsing,
clipboard, external submit) are enforced nowhere for managed desktop browser use:

1. The agent builds its browser broker with no gate and without `requireManagedPolicy`
   (`createProtocolBrowserControlBroker(context)` in `bootstrap/src/zcode-protocol/server.ts` and
   `server-operations.ts`). Browser commands from `node_repl` carry no `managed` context, so
   `authorizeBrowserComputerAction` returns `local_personal` and the command runs.
2. The server evaluates browser rules only when a decision carries `browser_action` or the call is
   browser-shaped. The only decision a managed run sends is for `mcp__node_repl__js`
   (`risk_class=mcp`, capability `mcp`), with no `browser_action`.
3. This is the open P05-INT-04 limitation: "The host still needs a concrete gate adapter and managed
   context propagation from the control-plane device transport." No production
   `BrowserComputerPolicyGate` implementation exists in LumiAgents.

## Affected phase and packets

- Phase: P05 (runs, tools, usage control); consumed by the desktop E2E (DE2E) claim D6.
- Contract Gate: `p05-cg-v1` (`p05-browser-computer-v1`).
- Active dependent packets: DE2E client/QA continuation.
- Merged dependent packets: P05-INT-04 (gates present, adapter missing), P05-CR-004 admission.

## Proposed change

Current: browser commands made inside an approved managed tool call are not evaluated against the
organization's browser policy; without a managed context they are treated as local-personal.

New:

1. **Fail closed now (client only, no contract change).** While a session's current turn carries
   a Lumi managed context, the agent's browser broker sets `requireManagedPolicy`. A browser
   command without a resolvable managed decision is refused with `managed_context_required` or
   `policy_unavailable`. `cancelRequest` stays exempt.
2. **Concrete gate (contract change).** Main implements `BrowserComputerPolicyGate` over the
   existing device transport. `resolveManagedContext` derives the context from the enclosing
   managed tool call (run, parent tool call, tool id/fingerprint, `action: "browser"`).
   `evaluate` posts one `POST /runs/{run_id}/tool-decisions` per browser command, with a derived
   tool call id and `browser_action`.
3. The server evaluates such a child decision with the browser rules and the parent call's
   **existing grant**. The MCP per-use floor is not applied again to each navigation; the child
   decision only narrows. Child decisions are audited with run, device and principal (F13
   acceptance).

## Why this is necessary

The runtime fault above shows that an organization's browser policy can be bypassed by any
approved Browser Use call. Without step 3, step 2 alone would demand an org approval for every
navigation and make managed browser use unusable.

## Compatibility impact

- API: step 3 adds a child-decision shape (parent `tool_call_id` + `browser_action`) to the
  tool-decisions route; existing decisions are unchanged.
- schema: possibly a nullable `parent_tool_call_id` on `tool_call_refs` (new forward-only migration).
- FE fixtures/types: run timeline/audit show child browser decisions.
- LumiAgents protocol: agent ↔ host browser broker gains the managed-session flag; Main gains the gate.
- migrations: as above, forward-only.
- security: closes a fail-open path; step 1 alone already removes the bypass.
- existing data: none.

## Alternatives considered

1. Treat every browser command as its own per-use approval: secure but unusable.
2. Server-side review of the `js` code string: the code is opaque JavaScript, so domains cannot be
   derived reliably; rejected.
3. Disable Browser Use in managed runs entirely: equivalent to step 1 until steps 2–3 land.

## Decision

Step 1 accepted under the existing P05-INT-04 contract ("managed requests require a valid policy
decision") and implemented in LumiAgents `91db7fb4` + `e9c1ffc2`: both `sendInput` call sites (protocol and v4
prompt turn) flag the session record when the input carries a managed context, and the broker then
requires a managed decision for that session's (or its child sessions') browser commands. The first
commit alone marked only the protocol path and the actual desktop still navigated; the journey caught
it. Unit regression:
`browser-control-broker.managed-policy.test.ts` (8/8; faulting the new condition fails exactly the
new case); related bootstrap suites 133/133. Runtime: the browser journey on `e9c1ffc2` refuses the
approved managed call's navigation ("This session is not authorized to run managed browser actions.")
with 0 page hits, where `f3d31d55` visited the page. Steps 2–3 are pending the P05 contract owner. Until then, managed desktop browser use is
**unavailable** (fail closed) rather than unenforced.
