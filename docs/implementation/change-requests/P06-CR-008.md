# Contract / Plan Change Request — P06-CR-008

Conformance repair for DE2E-INT-05 (race seam). **No frozen wire shape changes.** Claimed by
the race-binding implementer; the coordinator owns STATUS and may renumber.

## Trigger

Campaign evidence `automation-full-isolated-race-fail.{log,json}` (full actual isolated run,
profile `VPdMKK`): with the definition re-targeted to `eligible_device` and no workspace
binding, the due predicate admitted both active devices. The contested occurrence was claimed
and started by one of them, then settled `failed` / `run_activation_failed`. The P05 run it
created stayed `queued` with `workspace_binding_id = NULL`.

Cause, from source:

1. `DEVICE_DUE_OCCURRENCES_SQL` admitted any active device when
   `d.target_workspace_binding_id IS NULL`.
2. `start_occurrence` copied the definition's `target_workspace_binding_id` (NULL) into the
   P05 session and run.
3. Main requires `run.workspaceBindingId` to equal the binding it authorized for the original's
   workspace (`lumiManagedAutomationActivation.ts`) and refuses a NULL one. That refusal is
   correct and is not touched.
4. Nothing cancelled the run on the failed settlement, and the client's own cleanup read also
   rejects a NULL-binding run, so the queued run was orphaned.

## Affected phase and packets

- Phase: P06 (automations) over P03 device/workspace bindings and P05 runs.
- Contract Gate: p06-cg-v1 (wire shapes unchanged).
- Active dependent packets: DE2E-INT-05.
- Merged dependent packets: none changed.

## Proposed change

Current: a binding-less target admits every active device; `start` writes a NULL binding.

New (server-authorized, all from server rows for the **authenticated device**):

- Resolution: pinned binding -> must be that device's own live binding; binding-less -> the
  device's single live binding for the occurrence's project. Zero or several is refused; the
  server never guesses and never reads a client-supplied binding or identity.
- `due`: a binding-less occurrence is offered only to a device with exactly one live binding
  for the project, so a device that could never start it does not see it.
- `claim`: resolves before the attempt is allocated, so an unresolvable device spends no
  attempt budget and holds no lease. Stable reasons `workspace_binding_unresolved` and
  `workspace_binding_ambiguous` (409).
- `start`: resolves again and writes the resolved id to the P05 session and run; a batch guard
  asserts the binding is still live and the device's own, so a binding removed in between
  cannot be written.
- `settle` with outcome `failed`: the same batch cancels the occurrence's P05 run **only if it
  is still `queued`** and was created by this occurrence and lease
  (`failure_code = automation_run_not_started`, `run.cancelled.v1` system event). A run that
  already advanced (`running`, terminal) is untouched.

## Why this is necessary

Without it two eligible devices contend for work only one of them can legitimately execute,
the winner is arbitrary, and a failed activation leaves an unrecoverable queued run. A
binding-less run cannot be made valid by weakening Main.

## Compatibility impact

- API: no shape change. New 409 reasons on `claim` for a device with no/several bindings;
  `due` may omit work it previously listed for such a device.
- schema / migrations: none (uses `workspace_bindings`, `runs`, `run_events`).
- FE fixtures/types: none. LumiAgents protocol: none; Main guards unchanged.
- security: strictly narrower. No client value gains authority; Main authorization intact.
- existing data: occurrences already `started` with a NULL-binding run are not rewritten;
  they settle/expire as before. Probes that claimed with a binding-less device
  (`v01-lease-contention-probe`, `v01-attempt-exhaustion-probe`) now bind their devices first.
- Known limit: a device with several live bindings for one project cannot run a binding-less
  automation (ambiguous). Such an automation must be pinned to a binding. Selecting among
  several would need a new frozen field and is out of scope here.

## Alternatives considered

1. Let `start` accept a client-supplied workspace identity: rejected -- a client value would
   become the selector for authority, and it needs a wire change.
2. Allow a NULL-binding run and let Main bind later: rejected -- weakens Main's check.
3. Cancel orphans from the client only: rejected -- the client's own read of a NULL-binding
   run fails, and the server is the owner of the run.
4. Sweep stale queued runs on lease expiry: deferred (see follow-up); settlement cleanup covers
   the demonstrated seam.
