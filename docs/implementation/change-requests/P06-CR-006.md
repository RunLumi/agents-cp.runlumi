# Contract / Plan Change Request — P06-CR-006

## Trigger

Actual desktop adoption in the scheduler-skip-fixed runtime (retained profile
`lumi-automation-a-d14xCv`, D1 `scheduler-skip-fixed-d1`) generated `pending`
occurrences and queued `automation.dispatch` envelopes, then never produced a
lease, attempt or run: the schedule stage timed out at 360 s.

Call-path trace (source, not inference):

1. `generate_for_automation` inserts occurrences as `pending` and one
   `automation.dispatch` job row per occurrence (`dispatch_job_statement`).
2. The device due list (`DEVICE_DUE_OCCURRENCES_SQL`) returns only
   `state = 'dispatching'`, so a `pending` occurrence is invisible to every device.
3. Nothing moved `pending -> dispatching` in production. `dispatch_occurrence_statements`
   and `resolve_dispatch_plan` had no caller outside unit tests, and the
   `automation.dispatch` handler ran `run_lease_expiry_sweep`, the same work as
   `automation.expire_lease`.
4. Before CR-006 the jobs queue also had no automation producer
   (`dispatch_due_data_jobs` sent export/deletion jobs only); that half is
   already repaired in the producer projection and is not part of this CR.

## Affected phase and packets

- Phase: P06, consumed by DE2E-INT-05.
- Contract Gate: p06-cg-v1; wire shape, schema and migrations unchanged.
- Active dependent packets: DE2E-INT-05.

## Proposed change

Current: `automation.dispatch` sweeps expired leases; no code dispatches a
`pending` occurrence.

New: `automation.dispatch` decides ONE occurrence, from durable rows only.

- The job row (not the message) names the tenant and subject. The row must carry
  a valid organization and an `occ_` subject of type `automation_occurrence`;
  otherwise it is dead-lettered with `queue_job_scope_mismatch`.
- The occurrence is read by `(organization, occurrence)`; an absent occurrence,
  including another tenant's, is dead-lettered with
  `automation_occurrence_not_found` and nothing about it is written or disclosed.
  A missing automation is dead-lettered with `automation_not_found`.
- Only a `pending` occurrence is dispatched. Any other state (claimed, started,
  `ambiguous`, terminal) is left exactly as stored and the job completes as a
  duplicate. An `ambiguous` occurrence is therefore never replayed.
- For a `pending` occurrence the existing frozen decisions run unchanged and in
  their existing order: past the missed window -> `missed`; dispatch-time recheck
  (organization state, principal membership, policy version, license/entitlement)
  -> `skipped` with the stable block code; overlap policy from the occurrence's
  OWN immutable schedule revision -> dispatch, queue-one/cancel-previous hold, or
  skip. The result is `dispatching` with the frozen `dispatched` event.
- An automation that is no longer `active` (paused/suspended) does not dispatch:
  a slot that is not already `missed` is recorded `skipped` with
  `automation_not_active`. A later resume does not replay it.
- The job claim, the occurrence transition, its event and the job completion are
  ONE D1 batch. A refused guard (the occurrence moved after it was read) rolls the
  whole batch back and the job stays retryable; the next delivery re-reads state.

Unchanged: the direct device claim route still accepts `pending` and performs both
edges (`claim_performs_dispatch`); the device due list still returns only
`dispatching`; `automation.generate_occurrence` and `automation.expire_lease`
behaviour; the message envelope and its projection.

## Why this is necessary

Without it no scheduled occurrence ever becomes visible to a device, so managed
scheduled work cannot run end to end. Widening the due list to `pending` was
rejected because it would skip the dispatch-time recheck and the overlap decision,
which are the only places entitlement, membership and overlap are enforced before
a device sees work.

## Compatibility impact

- API/schema/FE types/protocol/migrations: none.
- Security: eligibility is re-read at dispatch; the message cannot grant authority;
  cross-tenant job rows are non-disclosing and write nothing.
- Existing data: `pending` occurrences left by earlier runs are dispatched or
  recorded `missed`/`skipped` by the next delivery of their (still `queued`) job.
  Occurrences of a paused automation become `skipped`, not claimable.
- Behavioural note for release handoff: a paused automation's pre-generated slots
  no longer reach a device through dispatch. The direct claim route is not changed.

## Alternatives considered

1. Make the due list return `pending`: rejected (bypasses recheck and overlap).
2. Dispatch from the cron sweep instead of the job: rejected; the job row is the
   durable, deduplicated record and the handler already owns claim/CAS/complete.
3. Dispatch inside `dispatch_due_data_jobs`: rejected; that is a producer, not a
   decision point.

## Addendum — delivery observability (no semantic change)

First runtime replay (retained `scheduler-dispatch-fixed`, profile
`lumi-automation-a-cyJ1zr`): jobs-queue delivery was proven (`p06_queue_routed:jobs`,
`QUEUE ... n/n`), yet job rows stayed `queued` attempt 1 lease 0 and occurrences
stayed `pending`, with no `p06_job_rejected`/`p06_job_failed` line. Guard inputs for
every pending row were independently read back as satisfied (org, principal, active
license, active automation), so entitlement/membership is NOT the cause.

The consumer acknowledged several outcomes silently: a body with no readable
`job_type`; any handler `Ok(_)` outcome; and, inside the automation handler, a guard
rollback and a settled duplicate, which map to the same coarse `Duplicate`. Absence
of rejection logs therefore proved nothing about which branch ran.

This addendum adds only bounded log lines, with no change to routing, acknowledgement,
retry or any statement:

- `p06_job_rejected:job_type_missing|job_type_unknown|job_type_unsupported` before routing.
- `p06_job_outcome:<data|automation|webhook|other>:<delivered|duplicate|retry_scheduled|dead_lettered|not_owned>`
  for every handler outcome.
- `p06_automation_job:<job_type>:<swept|dispatch_applied:<dispatched|queued|skipped|blocked|missed>|dispatch_already_settled|terminal_duplicate|guard_rollback|dispatch_refused>`.

Codes are fixed lowercase strings: never a job, org or subject ID, a reason text, a
body or a secret. Claim compare-and-set behaviour and guard-abort retry bounds are
deliberately NOT changed here; they need the actual branch proven first.

## Addendum — queue body serialization (root cause of the second stall)

Second runtime replay (retained `scheduler-observed`): with the observability above,
the actual log named the branch: `p06_job_rejected:job_type_missing`, then
`QUEUE ... 1/1`. The jobs consumer received a body with no readable `job_type`.

Root cause, from the pinned `worker` 0.8.6 and `serde-wasm-bindgen` 0.6.5 sources:
`Queue::send<T: Serialize>` calls `serde_wasm_bindgen::to_value` with the default
serializer (`serialize_maps_as_objects = false`), so a serde map -- including a
`serde_json::Value::Object` -- becomes a JS `Map`. A queue with `contentType: 'json'`
delivers a `Map` as `{}`. The producer projected each due row to a `Value` and sent
it, so BOTH envelope families (`DataJobEnvelope` and the strict automation
`QueueJobEnvelope`) arrived empty. The data-job path had the same defect and had never
run in a runtime. The outbox was unaffected because it sends a typed struct, which
serializes as an object.

Change: the producer crosses into JS through JSON text (`serde_json::to_string`, then
`js_sys::JSON::parse`, which cannot return a `Map`) and sends with `Queue::send_raw` and
`QueueContentType::Json`. No new dependency (`worker` re-exports `js_sys`). The
boundary refuses a body that is not a non-empty JSON object, or is larger than 64 KiB,
before it reaches the queue, so an empty `{}` is never published. Consumer validation is
unchanged and was NOT weakened to accept an empty body. Envelope fields, tenant hint,
reference and the no-content rule are unchanged; no migration, resource or production
change.

Controls: a disposable harness (`apps/api/scripts/v01-queue-body-serialization-probe.mjs`)
shows on the same local queue stack that a deep `Map` body arrives as `{}` (fault) while
a plain object parsed from JSON text arrives intact (positive control), for both
envelope families. A source pin fails if the producer calls the generic sender with a
`Value` again. Neither proves the Rust send path; a real Worker send -> queue consumer ->
D1 dispatch/claim/run/settle replay is still required.
