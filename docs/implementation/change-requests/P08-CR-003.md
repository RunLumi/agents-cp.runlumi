## Trigger

Source trace of `advance_adoption_stage` (`apps/api/src/routes/migration.rs`,
`StageTransition::Unchanged` branch): a credential-mode-only PATCH builds a response
claiming the requested `credential_mode`, `unchanged_stage: true` and
`version: body.version + 1`, but the batch contains only the version guard
(an `INSERT ... WHERE NOT EXISTS` that writes nothing when the version matches) plus
the event, audit and outbox rows. No `UPDATE` is pushed, so D1 keeps the old mode and
the old version. The first response is the unchanged row read back; the stored
idempotency body is the fabricated one; the next PATCH using `version + 1` fails the
guard.

**Runtime status: reproduced.** Coordinator run 10269 of the original reproducer
ended terminal FAIL 46/52 (log reported as `test-results/credential-mode-original-runtime.log`;
not readable from this checkout, so only the coordinator's summary is cited here):
six failures covering PERSISTED mode/version, REPLAY identical/stored, CHAINED
version and the stale-version refusal. Positive controls and tenant negative controls
ran. That output is the preserved failing evidence.

**Reproducer expectation corrected, not weakened.** The stale-version assertion
expected `details.reason = version_conflict`. A lost version guard goes through
`commit_mutation` -> `BatchOutcome::GuardLost` -> `domain_error(Conflict, "conflict")`,
so the route answers `409` with reason `conflict` before and after the fix. That
assertion was wrong independently of this defect and would have stayed red after a
correct fix; it now expects `409` / `conflict`. The negatives derive their stale version
from the D1 row at the time, so they do not depend on the old broken chain.

Reproducer (not yet executed, waiting for the runtime join):

## Proposed change

Current: the Unchanged branch persists nothing and reports `version + 1`.

New, within the existing route, statements, authorization and idempotency:

1. **Mode-only change** (`requested == current stage`, `next_mode != current_mode`)
   pushes the existing `advance_statement` with the current stage, current ownership,
   the new mode, the unchanged project/device ids and `expected_version = body.version`.
   The write and the `version + 1` increment are one guarded D1 batch with the existing
   guard, event, audit and outbox statements.
2. **Response and replay are the committed projection.** The stored idempotency success
   body is the record shape built from the row the guarded `UPDATE` produces (current row
   with the new mode, version + 1 and the request's `updated_at`). The first response is
   that exact stored success, served through the replay path; it is **not** re-read from
   D1 after the commit, because another writer's newer version could otherwise make the
   first response differ from a replay of the same key. A later `GET` may legitimately be
   newer. Compare-and-set, authorization and idempotency are unchanged.
   A completed replay is looked up **before** any check against the mutable current stage,
   so a retry of a committed request returns its stored response after the row has moved
   on; a new request must name the row's current version (`409 conflict` otherwise), which
   fences the projection against a guessed future version.
3. **Same-mode Unchanged** (`requested == current stage`, `next_mode == current_mode`)
   stays a replay-safe no-op: no `UPDATE`, no version increment, and the response is the
   current stored row. It must never report a version D1 does not hold. Recommended:
   no stage event, security event or outbox row for the no-op (decision D-a below).
4. Mode on a stage advance (`Applied`) is unchanged and already correct.

Explicitly unchanged: routes, request/response field names, enums, reason codes, stage
ladder, telemetry vocabulary, audit/outbox event names, schema, migrations,
`adoption.manage`, CSRF, `Idempotency-Key`, `credential_mode_permitted`, rollback to
`local_credential`, stage 5 denial, `deny_unknown_fields`, secret-free requests.

Decisions:

- **D-a (decided):** the same-mode no-op emits no stage event, audit row or outbox
  event, but the idempotency record is kept (completed) so a replay returns the same
  stored-row body. The version guard still leads the batch, so a stale caller cannot
  re-assert an old state. The shared commit helper requires an outbox slot, so the
  no-op passes a second existing version guard there (no new SQL, writes nothing).
- **D-b (decided):** a real mode change uses the existing `adoption.stage_changed`
  audit action and `adoption.stage_changed.v1` outbox event. Secret-free metadata keeps each
  family's existing stage keys (audit `from`/`to`, outbox `from_stage`/`to_stage`) and adds
  `from_credential_mode`/`to_credential_mode` (frozen label
  values only) and an accurate `stage_changed` flag (`false` for a mode-only change).
  Applied steps carry the same keys with `stage_changed: true`.
- **Response contract:** the first response, the stored idempotent body and every
  replay are the same stored value: the full binding record projection (the shape
  `GET .../bindings` serves) of the version this request committed.
  The same projection is now stored for an `Applied` step, whose replay previously
  returned a compact change body that differed from its own first response. Rollback
  has the same pre-existing first-versus-replay shape difference; that is recorded and
  intentionally not changed here (no broad refactor).

## Why this is necessary

P08-CG states that the wizard's "choose credential mode" step is its own request and
validates the mode on an unchanged stage. After the history-sync stage is disabled
(`history_sync_not_available`), `managed_policy` is the last reachable stage, so the
mode-only PATCH is the only way to change the mode there. Without persistence, the
desktop and the web adoption page would show different modes and the version chain
breaks. The `Applied` branch shows the intended statement list.

## Clarifications this CR records (no behavior change)

- The three modes are a **label**. No P08 route accepts, copies, fingerprints or
  downloads a secret. For `metadata_only` the gate sentence "holds a provider identifier
  and a fingerprint" describes no implemented code path; the truthful product reading is
  "this workspace is marked as keeping its own key; nothing about the key is sent".
  A real key fingerprint would need its own contract.
- The label is **separate from P04 execution credential policy**
  (`platform_only|organization_only|user_allowed|...`) and from `credentials` rows.
  It does not drive inference routing. The two enums share a name only.
- Local secrets are never exported by P08. An organization secret is never downloaded
  to the desktop.
- The server is **not** required to verify an active P04 organization credential before
  accepting `org_managed_credential`. Broadening it would need a frozen-CR decision and
  a new reason code; that is not proposed here.
- On PATCH every stage and mode refusal is `409 conflict` with the stable
  `details.reason` (`advance_adoption_stage` maps through `ApiErrorCode::Conflict`),
  while the gate's error table lists `credential_mode_requires_managed` as `422`.
  Clients key on `reason`. The table should be reconciled with the route in the
  coordinator's gate edit, not by changing behavior here.
- Stage 5 (`history_sync`) remains disabled and unreachable.

## Compatibility impact

- API: shape unchanged. A mode-only PATCH now stores what it reports; a no-op reports
  the stored version.
- schema: none. migrations: none.
- FE fixtures/types: none; `unchanged_stage` is no longer emitted in the mode-only
  response because the response becomes the stored record (the desktop `adoptionRecord`
  parser must be checked against the record shape before the fix; the web adoption page
  already reads the record shape).
- LumiAgents protocol: none.
- security: authorization, CSRF, idempotency, version compare-and-set and
  `credential_mode_permitted` all run before any write; no secret field is added;
  cross-tenant and member negatives are part of the reproducer.
- existing data: none stored by the defective path, so there is nothing to repair.
  Clients that sent a mode-only PATCH saw a success that D1 never held.

## Alternatives considered

1. Send the mode only with a stage advance. Rejected as the sole path: `managed_policy`
   is the terminal reachable stage while history sync is disabled.
2. A new route or a new reason code. Rejected: unnecessary surface and frozen
   vocabulary.
3. Have the client treat the mode-only response as untrusted and always re-read.
   Rejected as the only defense: the idempotent replay would still serve a body that
   D1 never held.
